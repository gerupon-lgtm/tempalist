# 実装タスク

上から順に実装する。P1〜P3の試用後にP4へ進む計画だったが、2026-09-10の発案者指示でPages公開・通知基盤接続確認に着手した。

要件定義書v1.14を基準とする。公開Originは `https://tempalist.sikumilab.com`、appIdはtempalist。v0.2.0でT-01〜T-20の実装を完了し、ユニットと隔離ブラウザで検証。基盤の公開鍵・CORS接続も成功。iOS/Android実機での通知表示・タップと長期試用は残件（notification-verification.md）。コード実装完了と実機配送検証完了を区別する。

## P0 基盤

### T-01 プロジェクト初期化とバージョン管理
- 静的配信構成（`index.html` / `src/*.js` / `sw.js` / `manifest.webmanifest`）、GitHub Pagesとカスタムドメイン設定
- 版数の正典を `src/version.js` の1箇所に置き、設定画面とmanifestに反映する
- 完了条件: `npm start` で起動し、設定画面に版数が出る
- 検証方法: 版数の反映先が複数ある場合の同値検証スクリプトを用意し、不一致で落ちること

### T-02 デザイントークンと共通UI
- `docs/screens.md` のトークンをCSS変数として実装。`font-family` を必ず指定する
- Google Fontsのゴシック系を使い、端末標準フォントをフォールバック指定する。発案者指定のNoto Sans JPを採用済み。配色は落ち着いたものとし、視認性を優先する
- 完了条件: `prefers-reduced-motion` に追従し、OSのダーク設定でも指定された白に近い背景を維持する
- 検証方法: 両メディアクエリを切り替えた表示確認、Webフォント取得失敗・オフライン時の標準フォント表示

### T-03 ストレージ層
- 全キーの読み書き、`schemaVersion` の付与、容量逼迫の検知
- 固定の件数・項目数上限は設けない。容量警告の検知方法・閾値（Q-03）は実装時に検証して記録する
- 完了条件: 保存失敗（QuotaExceededError）を検知して呼び出し元へ通知できる
- 検証方法: 保存失敗のモック、未知 `schemaVersion` の読み込み拒否、破損JSONの読み込み

## P1 テンプレート

### T-04 テンプレートCRUDと3状態
- 作成・編集・複製・削除、`draft` / `active` / `archived`
- 初回起動時に `docs/sample-templates.md` の5種を投入する。通常起動で再投入しない
- 完了条件: 状態別の一覧表示と、`active` のみが生成候補に出ること
- 検証方法: 各状態の遷移、`docs/要件定義書_テンパリストではない.md` 12章「状態×操作マトリクス（テンプレート）」の全マス

### T-05 テンプレート一覧画面（S-04, S-05）
- 完了条件: 0件時に新規作成へ導線が出る
- 検証方法: 空状態、50件時の表示

### T-06 項目の並べ替え（共通コンポーネント）
- v0.1.6: テンプレートに生成時の並び順ロック初期値を追加。リスト側で独立して切替可能。ONでは長押し・上下移動と保存層の順序変更を拒否する。旧データはOFFで補完。複製・共有・バックアップで保持する。
- ドラッグハンドルを450ms長押しすると半透明カードが追従し、移動先を表示する。PCも同操作、代替の「上へ／下へ」
- チェックリストとテンプレートで同一実装を使う
- ドラッグ中は画面上端・下端に近づけると、その方向へ自動スクロールする
- 完了条件: 並び順が即保存され、リロード後も維持される
- 検証方法: タップとドラッグの誤爆がないこと、項目1件・50件、画面端の自動スクロールとドラッグ終了・中断時の停止、スワイプに反応しないこと。50項目は性能基準であり、51項目以上の作成を拒否しない

## P2 チェックリスト

### T-07 生成（S-03）
- テンプレート選択、タイトル、期限（日付8桁補完・時刻4桁補完・ピッカー併用）
- `sourceTemplateId` を保持し、項目をコピーする
- 「空から作る」ではタイトルを入力して項目0件・`sourceTemplateId: null` で作成し、S-02で項目追加へ進める
- 完了条件: 生成後にテンプレートを編集しても、生成済みリストが変わらない
- 検証方法: コピー独立性、テンプレート0件で空から作成・項目追加・新規書き戻しができること、期限の時刻省略時に09:00補完、不正日付・貼り付け・途中入力

### T-08 詳細とチェック（S-02）
- チェック状態の保存、進捗表示、項目の追加・編集・削除
- 完了条件: 全操作がリロード後も維持される
- 検証方法: 項目0件、二重タップ、長いラベル

### T-09 一覧（S-01）
- 進行中／完了タブ、期限順、期限切れ強調
- 完了条件: 期限なしのリストも一覧に出る
- 検証方法: **JSTの0時前後・月末月初・UTCとJSTで日付が変わる時間帯**での期限切れ判定

### T-10 確定・演出・ロック・再オープン
- 確定ボタン、未チェック時の警告、編集ロック、確定日時の表示、再オープン
- 演出は点滅なしの1回フェード。`prefers-reduced-motion` では出さない
- 完了条件: 確定後にすべての編集操作が拒否され、再オープンで戻る
- 検証方法: 未チェックのまま確定、確定済みの編集試行、再確定で `settledAt` が上書きされること

### T-11 書き戻し（S-06）
- 上書き／新規登録の選択、確認ダイアログ、アーカイブ先は `active` へ戻す
- 下書き先への書き戻しは `draft` を維持する。有効化は利用者操作で行う
- 完了条件: 元テンプレート不在なら新規のみが出る
- 検証方法: 3状態それぞれへの上書き、元削除済み、並び順とメモが維持されること

## P3 データ移動

### T-12 エクスポート／インポート
- JSON書き出し・取り込み。**通知関連キーを含めない**
- リスト・テンプレートは既存データを上書き・削除せず追加する。同じファイルの再取り込みも別データとして追加する。ID衝突時は新IDへ振り直し、元テンプレートとの参照も合わせて変換する
- バックアップ内の設定では上書きせず、移行先の設定を維持する。取り込んだデータにも移行先の保持期間・容量整理方針を適用する（Q-11確定済み）
- 完了条件: 取り込んだチェックリストが `notificationEnabled: false` で入る
- 設定の検証: 移行元と移行先で保持期間が異なる場合も移行先の設定を維持する。特に移行先が `keep` なら期間経過・容量不足でも自動削除せず、他の設定では移行先の保持期間で判定する
- 検証方法: 未知 `schemaVersion` の拒否、破損ファイル、ID衝突時の参照維持、同一ファイルの再取り込みで既存データを変えず別データが追加されること、通知資格情報が出力に含まれないこと

### T-13 テンプレートのURL・JSON共有（S-08）
- 生成側と取り込み側。取り込みは必ず `draft`
- URL長超過時はリンク生成を中止して理由を表示し、テンプレート1件の共有JSONをダウンロードできるようにする。共有JSONの取り込みも内容確認後に下書きで追加する
- URL長上限の数値・計測方法（Q-04）は実装時に検証して記録する
- 完了条件: 共有前に個人情報の注意喚起が出る
- 検証方法: 長大テンプレートでのURL長境界、共有JSONの往復で名前・項目・メモ・並び順が維持されること、下書き登録、改竄されたパラメータ、未知版・破損JSONの拒否

### T-14 設定・保持期間・自動削除（S-07）
- 保持期間の選択、`settledAt` 起算の自動削除、容量逼迫時の警告と古い完了リストの削除
- 「削除しない」では容量不足でも自動削除せず、エクスポート・手動削除を案内する。他の設定で保持期間内の完了リストを削除する場合は、対象件数を示し利用者の確認後に削除する
- 容量不足で新規保存できない場合は「次のリストを作成するには保存済みデータを削除して空き容量を確保する必要がある」旨を画面表示する。キャンセル時は削除せず入力を保持する
- 完了条件: **未完了リストとテンプレートが自動削除されない**
- 検証方法: 保持期間境界（当日・翌日）、「削除しない」での容量不足でも自動削除されないこと、期間内の候補件数表示と承認・キャンセル、新規作成できない旨の案内、保存再試行

- `docs/api-design.md` §5 のフロー。通信は `src/notification/api.js` に閉じ込める

- 完了条件: API不通でもチェックリストの保存が完了する

### T-18 予約計算とキー振り分け
- オフセット→絶対時刻、`deadline_advance` / `deadline_imminent` の判定
- 完了条件: 過去になる枠を登録しない
- 検証方法: **境界（残り2時間ちょうど）**、時刻省略時の09:00解釈、`TZ=UTC` のCIで期待どおりになること

### T-19 Service Worker の受信・表示・遷移
- 完了条件: `docs/api-design.md` §8 の8項目すべてを検証してから表示する
- 検証方法: appId不一致、未知キー、不正UUID、余分フィールド、payload文字列をURLとして開かないこと、同じ `groupId` のみ集約、既存画面のfocus

### T-20 起動時修復
- 完了条件: 起動を繰り返しても予約が重複しない
- 検証方法: 対応表が欠けた状態、購読失効（401/404）、オフライン復帰
