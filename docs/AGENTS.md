# AGENTS.md — `!=テンパリスト`（NOT EQUAL TEMPALIST / appId: `tempalist`）

テンプレートから起こす使い捨てチェックリストのPWA。型（テンプレート）と実体（チェックリスト）を2層で管理し、期限に応じて端末へプッシュ通知を出す。

- 要件定義書: `要件定義書_テンパリストではない.md`（v1.13）が正典。仕様の疑義はこれを見る
- 詳細設計: `docs/data-model.md` / `docs/screens.md` / `docs/api-design.md` / `docs/tasks.md`
- 実装順: `docs/tasks.md` の T-01 から順に進める
- サンプル5種の項目: `docs/sample-templates.md`
- 通知基盤のRegistry登録完了。v0.2.0で6API・端末登録・Outbox・予約取消・SWを実装済み。公開OriginのGET/CORS成功。ローカルOriginは未許可。実機配送チェックはdocs/notification-verification.md。

## 技術スタック

- 素のHTML / CSS / JavaScript（ESM）。**フレームワーク・バンドラを導入しない**
- 配信: GitHub Pages（カスタムドメイン `https://tempalist.sikumilab.com`）
- 保存: localStorage のみ。サーバーに業務データを置かない
- PWA: Web App Manifest ＋ Service Worker
- 通知: 通知共通基盤 v2 API（`appId=tempalist`）
- テスト: vitest ＋ jsdom。**開発時のみのdevDependency**で、配信物に含めない
- フォント・アイコン: `docs/screens.md` の「デザイントークン」節に従う

## 変更禁止事項（根拠つき）

次は検証済み・合意済みの決定であり、「改善」しないこと。

1. **通知APIへタイトル・本文・URL・業務データを送らない。** v2契約はstrict schemaで、余分なフィールドは400になる。加えて「中身をサーバーに置かない」がこのアプリの前提（要件定義書0章C-1）
2. **起動のたびに `reminderId` を再発行しない。** 重複通知になる（v2仕様 §10.3）。同じ論理通知枠には既存IDを再利用する
3. **Push payload 内の文字列をURLとして直接開かない。** `routeKey` を Service Worker 内の固定表で相対パスに解決する（v2仕様 §9）
4. **同じ操作の再送には同じ `Idempotency-Key` を使い、内容を変えたら新しいキーにする。** 使い回すと409になる
5. **`deviceId` / `deviceSecret` をエクスポートJSONに含めない。** 購読は端末に紐づくため、他端末へ渡しても動かないうえ、資格情報の流出になる
6. **テンプレートの変更を実行中のチェックリストへ反映しない**（コピー方式）。型を育てる経路は書き戻しだけ
7. **自動削除の対象は完了チェックリストのみ。** 未完了リストとテンプレートを自動で消さない
8. **未知の `schemaVersion` は取り込みを中止する。** 推測して読まない
9. **400 / 403 / 409 / 413 は自動再送しない。** 再送してよいのは通信断・429・500・503のみ（429は `Retry-After` を尊重）
10. **`/v1/` のエンドポイントを呼ばない。** v1はあとキュー専用であり、共通基盤側のコードも変更しない

## 日時・タイムゾーン

- **保存・API・ログはUTC正規化**。交換形式は ISO 8601 で必ず `Z` で終える
- **表示・入力は端末のタイムゾーンに追従**し、取得できない場合は `Asia/Tokyo` にフォールバックする
- タイムゾーンは固定オフセット（`+09:00`）ではなく **IANA ID**（`Asia/Tokyo`）で保持する
- **期限の時刻が省略された場合、ローカル日付の 09:00 として解釈**してからUTCへ変換する
- 通知オフセットは**相対値で保持**し（`-24h` / `-1h`）、送信直前に期限から絶対時刻を計算する
- 禁止: サーバーのローカル時刻依存、`new Date("2026-09-09")` の暗黙UTC解釈に頼った日付判定、固定オフセットの埋め込み
- CIは `TZ=UTC` で実行する。JST依存のロジックが混入していれば落ちる

## 前提（仮置き。実装中に変わりうる）

- v0.1.6の画面・操作は発案者確認済み。v0.2.0は通知機能・オフライン起動・ヘッダ下の薄い区切り線を追加。アイコン・チェック・主要ボタンはコーラル #f5614c、背景 #fffefe。カード全体の長押し（チェック領域・右端を除外）と右端↑↓を試用中。最新の確認版はscreens.mdを参照し、最終承認後に要件・タスクへ一括反映する。書体は発案者指定のNoto Sans JPで確定し、標準フォントへのフォールバックを指定。実画面での書体・操作感の確認はT-22
- `deadline_imminent` に切り替える閾値は「期限まで残り2時間以内」
- 容量警告はlocalStorage全キー・値のUTF-16概算4MiB以上。実際の保存成功／QuotaExceededErrorを最終判定とする
- 共有URL全体で8000文字まで。HTTPで内容を送らない `#t=` 形式。超過時は共有JSONへ切り替える

## 規約

- バックアップ取り込みはリスト・テンプレートを追加し、設定は移行先のものを維持する。取り込んだデータにも移行先の保持期間・容量整理方針を適用する
- 完了リストの保持期間は確定日時を起算点として既定90日。設定の選択肢は30日／90日／1年／削除しない（要件定義書Q-06で確定済み）
- 「削除しない」では容量不足でも自動削除しない。他の保持期間で期間内の完了リストを削除する場合は、対象件数を示して確認を得る。空き容量を確保しないと次のリストを作成できない旨も画面表示する
- テンプレート数・チェックリスト数・項目数の固定上限は設けない。50項目は操作性の検証基準
- 「空から作る」は `sourceTemplateId: null` で生成する。下書きテンプレートへの書き戻しは下書きを維持する
- 1ファイル1責務。通知API通信は `src/notification/api.js` に閉じ込め、他から通知APIへ `fetch` を直接呼ばない。Google Fontsの読み込みは別途許可する
- 業務データの保存と通知同期を分離する。**通知APIの失敗で利用者の入力を取り消さない**
- Service Worker は依存を持たない単一ファイルとして書く
- アイコンライブラリを混在させない（`docs/screens.md` の指定に従う）

- 並び順ロックはテンプレートのdefaultOrderLockedを生成時にコピーし、Checklist.orderLockedで独立管理。旧データはfalse。ロック中の順序変更を保存層でも禁止する。詳細はdata-model.mdのv0.1.6節を参照。
