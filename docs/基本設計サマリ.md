- モード: 新規モード

## 1. 全体構成

```
[ブラウザ / PWA]  https://tempalist.sikumilab.com
  ├─ UI（素のHTML+ESM、ビルドなし）
  ├─ localStorage … テンプレート・チェックリスト・設定（業務データはここだけ）
  ├─ 通知クライアント（src/notification/api.js に閉じ込め）
  │     └─ Outbox / 冪等キー / 再試行 / 起動時修復
  └─ Service Worker … Push受信、固定文面の表示、/list への遷移
              │
              ▼ v2 API（appId=tempalist）
[通知共通基盤]  端末登録・匿名予約・配送・再試行・失効処理
              ※ 変更対象外。中身（タイトル・本文・URL・業務データ）は一切渡さない
```

## 2. 技術選定と根拠

| 判断 | 選択 | 根拠 | 覆す条件 |
| --- | --- | --- | --- |
| フロント構成 | 素のHTML＋ESM（バンドラなし） | GitHub Pagesへ直接配信でき、Service Workerもビルド不要。依存の陳腐化が少ない | 画面状態の管理が破綻したら軽量フレームワークを検討 |
| 通知クライアント | 自前実装（通信を1ファイルに隔離） | `packages/notification-client` は共通基盤の実装完了後に配布されるもので現時点で存在しない。疎結合のほうが基盤側の変更に巻き込まれない | 配布後に差し替え可能な境界を維持する |
| テスト | vitest ＋ jsdom（開発時のみ） | 配信物をビルドなしに保ったまま、日時境界と異常系を機械的に検証できる | — |
| notificationKey | 2種類（`deadline_advance` / `deadline_imminent`） | 前日と直前で文面が同じだと緊急度を判断できない | 利用者が任意オフセットを多用し2分類で足りなくなった場合 |
| routeKey | `list` の1種類 | 遷移先はチェックリスト詳細のみ。対応は端末内の対応表で解決する | 一覧など別の入口が必要になった場合 |
| 日時 | UTC保存・ローカル表示・JSTフォールバック | 通知予約がUTC必須。表示のずれは最も事故が多い | — |
| フォント・トンマナ | Google Fontsのゴシック系＋標準フォントのフォールバック。落ち着いた配色・視認性重視 | 発案者指定。日常・工場・研究室で使いやすくする | 書体・色・余白はT-22で選定・調整 |

## 4. 調査根拠と合意済みの契約

- **本文・タイトル・URL・業務データを拒否するstrict schemaを使う**。再利用調査の契約テスト実績は既存v1に関するもの。v2でも同じ制約を採用する承認済み仕様だが、v2の実装検証・稼働確認は後回し
- **`deviceId` / `deviceSecret` は端末とOriginに紐づく**。JSONで別端末へ移しても通知は動かず、資格情報の流出になるだけ。したがってエクスポート対象外
- **Originを変更するとPush購読が無効になる**。購読はOrigin単位のため、公開後のドメイン変更は利用者の再設定を強制する
- **起動のたびに `reminderId` を発行すると重複通知になる**（v2仕様 §10.3 が明示）
- **iOSのプッシュはホーム画面追加済みのPWAでのみ動作する**。スマホ中心の本アプリでは追加導線が必須機能

## 5. 実装順

P0 基盤 → P1 テンプレート → P2 チェックリスト → P3 データ移動 → **（自分で数週間使う）** → P4 通知 → P5 仕上げ。

P4の前に一度止めるのは、要件定義書の反証質問で「作らなくても何も起きない」「利用者に聞いていない」と確認したため。棄却条件が「自分が使わなくなったとき」である以上、**最初の検証対象は作成者自身**であり、使われないと判明した場合に通知実装を回避できる。

## 6. 着手前に必要な外部作業

**進行状況（2026-09-09、発案者確認）**：通知共通基盤v2は別途並行して実装中。実装・デプロイ完了の確認と実機連携の検証は、発案者の指示により後回しとする。本書の共用方針・通信契約の確定は、v2の稼働確認済みを意味しない。P0〜P3の設計・実装は進められる。

1. `tempalist.sikumilab.com` のDNSとGitHub Pagesカスタムドメイン設定（**301リダイレクトでは不可**。Originがgithub.io側になる）
2. 共通基盤のApplication Registryへ `appId=tempalist`、Origin、`notificationKey` 2種、`routeKey` 1種、専用VAPID鍵を登録（基盤管理者の作業）
3. 開発用Origin（localhost）の登録

1と2が済むまで、P4は着手できない。P0〜P3は影響を受けない。
