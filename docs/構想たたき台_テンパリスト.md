## 1. 背景と課題

同じことを繰り返しやっているのに、確認事項は毎回頭の中から引っぱり出している。しかも場面ごとに中身が違う。

- **おでかけ**：財布、充電器、鍵、天気の確認……行き先が変われば持ち物も少し変わる
- **納品前**：ファイル名、動作確認、送付先、控えの保存……案件ごとに1〜2項目だけ違う
- **顧客訪問**：資料、名刺、訪問先の情報、前回の宿題……訪問先ごとに1〜2項目だけ違う

紙のチェックリストや固定のメモだと、**「毎回ほぼ同じ、でも少しだけ違う」**を扱えない。1本の固定リストにすると使わない項目が混ざり、都度メモを書き起こすと結局抜ける。

## 2. アイデアの核

**チェックリストを「型（テンプレート）」と「実体（1回きりのリスト）」の2層に分ける。**

型は繰り返し使う資産としてマスタ画面で管理する。実際に使うときは型から1件コピーして、タイトルと期限をつけ、その回だけの項目を足したり消したりする。コピーした後は型と切り離された独立のリストになり、**実際に使って形が良くなったリストは、型に書き戻せる**。

流れは一方通行に保つ。**型→実体は生成時の一度きり。実体→型は書き戻しのときだけ。**

## 3. 想定ユーザーと公開の方針

- **誰が使うか**：SIKUMI LAB のツール群の1つとして**一般公開**する。決まった段取りを繰り返す人全般（個人事業主、フリーランス、旅行や外出の準備をする人など）
- **データの持ち方**：**1人完結・端末内保存**。ログイン・アカウントなし。リストやテンプレートの中身はサーバーに送らない
- **例外はプッシュ通知だけ**：サーバーが知るのは「どの購読宛に、いつ、どの識別子で鳴らすか」だけ。端末が通知を受け取ってから、自分の localStorage を見て内容を組み立てて表示する
- **収益化**：しない（SIKUMI LAB の既存方針を踏襲）**【想定】**

## 4. 初めて使う人の1周（初回価値）

1. URLを開く。**サンプルのテンプレートが最初から3種類入っている**（おでかけ／納品前／顧客訪問）**【想定】**
2. 「おでかけ」を選ぶ → タイトル「9/20 京都日帰り」と期限を入れ、**このリストの通知をONにする**
3. 生成されたリストに、その回だけの項目「京都の乗換メモを印刷」を足す
4. 期限の前に端末へ通知が届く。準備しながらチェックしていき、全部つけば完了
5. うまくできたリストは**テンプレートに書き戻す**。次の外出では、育った型からまた1件起こす

初回にテンプレートが空だと何も始められないため、サンプル同梱は必須。空から作る導線も併せて用意する**【想定】**。通知の許可を求めるのは初回起動時ではなく、**最初に通知をONにした時点**にする。

## 5. 機能の種

### テンプレート管理（マスタ画面）
- テンプレートの作成・編集・複製・削除
- 各テンプレートは「名前」と「項目の並び」を持つ
- 実行中／実行済のチェックリストからの**書き戻し**を受け取る
- 項目にメモ／補足を持たせるか **【要確認】**
- テンプレートの並べ替え・アーカイブ **【想定】**

### リストの生成と管理
- テンプレートを選んでリストを生成。生成時に**タイトル**と**期限**を入力
- 生成したリストは**生まれ元のテンプレートIDを保持する**（書き戻し先の判定に使う）
- 生成後は独立したリストとして、項目の追加・編集・削除・並べ替えが自由
- **テンプレートを後から変更しても、動いているリストには反映しない**（コピー方式）
- チェック状態の保存、進捗（3/8 など）の表示 **【想定】**
- リスト一覧を期限順に表示。期限切れは強調 **【想定】**

### テンプレートへの書き戻し
- 実行中・実行済のリストを、テンプレートとして保存し直せる
- 保存時に**「元のテンプレートを上書き」か「新しいテンプレートとして登録」かを選択**する
- 上書きは確認ダイアログのみ。世代管理・元に戻す機能は持たない
- **生まれ元のテンプレートが存在しない場合**（削除済み／インポートで入ってきた等）は、新規登録のみを提示する
- 書き戻すときにチェック状態・タイトル・期限は落とし、項目の並びだけを型にする **【想定】**

### 期限と通知
- 期限は**日付＋時刻**を持てる。時刻を省略した場合の扱い **【要確認】**
- **通知のON/OFFはチェックリスト単位**
- **通知スケジュールは1リストにつき複数持てる（配列）**。「期限の1時間前」「前日」など
- スケジュールは**絶対日時ではなく、期限からの相対オフセットで保持する**。期限を変えたら、ON中のリストの予約を機械的に作り直す
- 既定のオフセット（初期値として何を入れるか） **【要確認】**
- 新規リストの通知は既定OFF **【想定】**（初回に許可を求めて拒否されると復帰しにくいため）
- 実装方式は**「あとキュー」で実績のある構成を流用**：OCI 上のバックエンドが指定時刻に端末へプッシュを送り、端末は自分の localStorage を見て内容を組み立てて通知する
- 通知を拒否された場合は、アプリ内の期限強調表示のみで成立させる **【想定】**

### 通知の登録タイミング（すべての経路で共通）
- **リストの通知がONにされた時点**で、購読情報と期限・オフセットをサーバーに送って予約を作る
- OFFにしたら予約を消す。期限を変えたら、ON中のものだけ作り直す
- 新規作成・インポート・期限の後付けを区別しない。**インポートは「OFFの状態で入ってくる」だけ**
- **期限を過ぎているリストは通知トグル自体を無効化する**（期限を先に更新すればONにできる）

### 完了したリストの扱い
- 履歴として残す（書き戻しの対象になるため）**【想定】**
- 保持期間・自動削除・手動削除の要否 **【要確認】**

## 6. 実現方式：竹（確定）

| | 内容 | 判断 |
| --- | --- | --- |
| **梅** | 単一HTML＋localStorage、GitHub Pages のみ | 採らない。通知が実現できない |
| **竹** | 梅＋**PWA化**＋**JSONエクスポート／インポート**＋**OCI上の通知バックエンド**（あとキュー方式） | **採用** |
| **松** | アカウント＋クラウド保存で自動同期・複数人共有 | 採らない。1人完結の方針と衝突 |

竹の内訳：

- **フロント**：ビルド工程なしの静的ファイル。GitHub Pages に配置 **【想定】**
- **保存**：localStorage。JSON でエクスポート／インポートできるようにして、ブラウザデータ削除による全消失に備える
- **エクスポート形式**：ファイル先頭に `schemaVersion` を持つ。読み込み時に**知らない版番号なら取り込みを止め、理由を表示する**
- **通知**：Service Worker ＋ Push API。購読情報と通知時刻だけを OCI のバックエンドに登録。あとキューの構成を流用
- **通知は端末に紐づく**。JSONを別端末にインポートしても購読は引き継がれないため、取り込んだリストはOFFで入り、その端末でONにした時点で新たに予約が作られる
- **iOS の制約**：iOS Safari のプッシュはホーム画面に追加した PWA でのみ動作するため、iPhone 利用者には追加を促す導線が要る **【想定】**

## 7. 設計上の確定事項（要件定義の前提）

1. **型と実体はコピー方式**。テンプレートを直しても、動いているリストには反映しない
2. **型を育てる経路は書き戻しのみ**。上書きか新規かは利用者が選ぶ
3. **通知はONにした操作を起点に、その端末の購読で予約する**。経路（新規／インポート／期限の後付け）で分岐させない
4. **通知スケジュールは配列＋相対オフセット**。UIが当日1回のみでも、構造は最初から複数対応にする
5. **エクスポートJSONは版番号を持つ**。後付けが効かないため第1版から入れる

## 8. 残っている論点

### 要件定義で決めるもの
- 期限に時刻を入れなかった場合の扱い（既定時刻を置くか、日付のみの通知にするか）
- 既定の通知オフセット（初期値として何を入れておくか）
- 新規リストの通知既定値をOFFにしてよいか **【想定】** の確認
- 完了リストの保持期間・削除
- テンプレートの状態（有効・下書き・アーカイブ）と選択画面での見え方
- テンプレート数・リスト数の上限、localStorage 容量超過時の挙動
- 項目のメモ・補足欄の有無
- サンプルテンプレートの同梱内容

### 基本設計で決めるもの
- **通知予約の後始末**：完了・削除時のクライアントからの取り消し、期限超過予約の自動削除、恒久エラーを返す購読の削除。**あとキューの実装と照合して確定**（端末側でデータを消した場合、サーバーに予約が残っていても localStorage に情報がないため通知は表示されない、という挙動を確認済み。誤通知にはならないため、残るのはサーバー側にゴミが溜まる運用面のみ）
- バックエンドの構成（あとキューと共用するか、分離するか）
- iOS のホーム画面追加を促す導線
